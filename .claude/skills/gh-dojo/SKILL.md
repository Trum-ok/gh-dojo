# Задачи gh-dojo через `gh dojo`

Процесс описан в `.github/dojo.toml` (пресет `kanban`). Задачи ведутся **только** через `gh dojo`: не трогай статусы,
комментарии, связи и новые issue через `gh issue` / `gh project` / GraphQL. Исключения — только то, чего в gh-dojo
нет (см. «Чего нет в gh-dojo»).

**Начни с `gh dojo describe`**: глаголы этого проекта, когда их применять, что они требуют и делают заодно, жизненный
цикл и коды выхода — коротко, без сети. `gh dojo <глагол> --help` — подробности одного глагола. Сомневаешься — читай
их, а не угадывай: таблицы переходов и кодов здесь нарочно не повторяются. `gh dojo doctor` — если что-то не так с
настройкой (токен, доска, конфиг): каждая проблема — с командой исправления.

## Жизненный цикл

`Backlog` → `In progress` → (`Waiting`) → `Ready` (закоммичено в main) → `Done` (вошло в релиз). Глаголы: `start` —
берёшь в работу, `wait` — работа встала, `ready` — сделано и в main, `done` — вошло в релиз.

- Issue без статуса или не на доске считается `Backlog`; любой глагол сам добавляет issue на доску.
- `start` оставляет комментарий «Взял в работу. Сессия: <ссылка>» (из `CLAUDE_CODE_HOST_SESSION_ID`; нет переменной —
  предупреждение, не ошибка). `--comment "…"` дописывает текст. Если у задачи есть неснятые блокеры, `start`
  **предупреждает** о них в stderr и всё равно выполняется: прочитай `show N` и реши, можно ли браться, или спроси
  пользователя.
- `wait` **требует** `--by` или `--comment` (иначе код 1). `--by 12` / `--by "#12"` → «Ждём #12.» и заодно связь
  blocked-by: #12 блокирует задачу. Несколько — через запятую: `--by 12,13`. `--by "решения пользователя"` — только
  комментарий; номера вперемешку с текстом — код 1. Номер pull request попадает в комментарий без связи. Когда блокер
  снят — снова `start N`.
- `ready` — только когда изменение **в main** (смёрджено, тесты зелёные), а не когда готово на ветке.
- `done` — только когда изменение вошло в релиз; без указания пользователя не ставь. `done` заодно **закрывает** issue
  как completed; уже закрытая (например, PR с `Closes #N`) остаётся закрытой (`already closed as completed`).
- `ready` и `done` пишут комментарий только с `--comment`; полезно указать коммит или релиз: `--comment "5fc0e30"`.
- Подтверждение — одна строка, перечитывать задачу не нужно: `#42 Backlog → In progress, comment left`.
- `gh dojo <глагол> N --dry-run` — план без изменений: статус, связи, какой комментарий уйдёт.

**Блокер снят**, когда он закрыт или стоит на доске в статусе из `statuses.resolved` (здесь `Ready`, `Done`): задача в
`Ready` сделана, хотя issue ещё открыта. Блокер, чей статус прочитать не удалось (`status not read: …`), — неснятый.

## Несколько задач за раз

`done` принимает несколько номеров: `gh dojo done 12 13 14` после релиза. Каждая задача проверяется и пишется
отдельно: неудачная пропускается, остальные идут дальше; в конце итог `3 of 3 done` или ошибка со списком того, что не
сделано, и причинами. Повтор той же команды трогает только недоделанное. Остальные глаголы принимают один номер.

## Чтение

- `gh dojo show N` — **перед началом работы**: статус, milestone, блокеры в обе стороны (неснятые первыми, у каждого
  статус на доске), история, описание, последние 5 комментариев. `show 12 13 --brief` — по три строки на задачу;
  `--comments all` — весь тред (до 100); `--full` — без обрезки.
- `gh dojo list` — открытые задачи по статусам (Done и закрытые скрыты со счётчиком). Фильтры: `--status "In progress"`,
  `--status none`, `--mine`, `--label bug`, `--all`, `--limit 100`.

## Запись

- `gh dojo new "<заголовок>" --type <bug|enhancement|documentation|dogfood> --body "…"` — issue + метка + доска +
  `Backlog` одной командой. Длинное описание: `--body-file file` или `--body-file -` (stdin). Ещё метки: `--label X`.
  `--milestone "<название>"` — открытый milestone (неизвестный — код 1 со списком). `--blocked-by 12` — сразу
  заблокирована #12 (повторяется или через запятую; несуществующий номер — код 3, ничего не создаётся). Заголовок с
  `-` — после `--`, все флаги — до `--`: `gh dojo new --type bug -- "-v is ignored"`.
- `gh dojo comment N "текст"` или `gh dojo comment N --body-file -` — комментарий без смены статуса.
- `gh dojo block N --by M` — связь «N заблокирована M» без смены статуса; `gh dojo unblock N --by M` — снять её.
  `--by` повторяется или через запятую; другой репозиторий — `owner/repo#12` или ссылка. Уже существующая (или уже
  снятая) связь — не ошибка (`already`). Pull request блокером быть не может (код 3); цикл — код 1.

## JSON

Любая команда принимает `--json`, `--jq '<выражение>'` и `--template`, как gh. Ошибка в этом режиме — тоже JSON (поле
`error` с `exit_code`, `message`, `allowed`, `fix`), код выхода тот же. Пригодится, когда нужно разобрать вывод:

```sh
gh dojo list --jq '.issues[] | select(.status == "Ready") | .number'
gh dojo show 42 --jq '.issues[0].blocked_by[] | select(.resolved | not) | .ref'
```

Для обычной работы хватает текстового вывода: он короче.

## Коды выхода

Полный список — в `gh dojo describe`. Главное: при ошибке читай строки `error:` / `allowed:` / `fix:`; код 2 — отказ
проверки процесса: **не обходи** его (не двигай статус другим путём), спроси пользователя; коды 4 и 5 — повтори
**ту же** команду (4 — чуть позже).

Повтор безопасен: глагол не меняет уже выставленный статус и не пишет комментарий, если он уже последний от gh-dojo;
`comment` не дублирует свой последний комментарий; `block` / `unblock` пропускают связи, которые уже как надо; `new` с
тем же заголовком доделывает уже созданную issue, а не заводит вторую.

Глагол с `confirm = "user"` (в нашем конфиге таких нет) — решение пользователя: без `--yes` код 2. Спроси
пользователя и повтори с `--yes`, только если он согласен; сам `--yes` не дописывай.

## Неудобство → задача `dogfood`

Любое неудобство при работе с gh-dojo (непонятная ошибка, лишний шаг, не хватает флага, справка врёт, пришлось
обойти через `gh`) — **сразу** заводи задачу, не откладывая и не чиня молча:

```sh
gh dojo new "<что неудобно, кратко>" --type dogfood --body "Что делал: … Что ожидал: … Что получил: …"
```

Затем продолжай основную задачу.

## Чего нет в gh-dojo

Здесь допустим `gh`, но только когда это нужно по задаче или просит пользователь:

- закрыть issue не через `done` (не нужна, дубль) или переоткрыть — `gh issue close N --reason "not planned"` /
  `gh issue reopen N`, только по решению пользователя (глаголов `drop` и `revive` в нашем конфиге нет);
- поправить заголовок, описание, метки или исполнителей существующей issue — `gh issue edit N …`;
- `next`, `release`, `agent install` — v0.2 (этот skill пока написан вручную).

## Какая версия работает

Установленный `gh dojo` — сборка последнего `make install` из main, а не текущей ветки: сломанная ветка не ломает учёт
задач. Новое поведение из ветки в `gh dojo` не появится, пока его не смёрджат в main и не переустановят:

```sh
gh dojo --version   # git describe установленной сборки
make install        # в рабочей копии на main, после мёрджа
```
