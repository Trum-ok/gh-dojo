# Задачи gh-dojo через `gh dojo`

Процесс описан в `.github/dojo.toml` (пресет `kanban`). Задачи ведутся **только** через `gh dojo`: не трогай статусы,
комментарии и новые issue через `gh issue` / `gh project` / GraphQL. Исключения — только то, чего в gh-dojo ещё нет
(см. «Чего нет в v0.0»).

Справка — контракт. `gh dojo --help` показывает глаголы с их `when`, жизненный цикл (раздел Lifecycle: из каких
статусов в какой ведёт каждый глагол, начальный, финальный и «снятые» статусы) и коды выхода с тем, что делать после
каждого. `gh dojo <глагол> --help` — что обязательно и какой комментарий уйдёт. Сомневаешься — читай её, а не
угадывай: таблицы переходов и кодов здесь нарочно не повторяются.

## Жизненный цикл

`Backlog` → `In progress` → (`Waiting`) → `Ready` (закоммичено в main) → `Done` (вошло в релиз). Глаголы: `start` —
берёшь в работу, `wait` — работа встала, `ready` — сделано и в main, `done` — вошло в релиз; переходы — в
`gh dojo --help`.

- Блокер **снят**, когда он закрыт или стоит на доске в статусе из `statuses.resolved` (здесь `Ready`, `Done`):
  задача в `Ready` сделана, хотя issue ещё открыта. Блокер, чей статус на доске прочитать не удалось (`show` пишет
  `status not read: …`), считается неснятым.
- Issue без статуса или не на доске считается `Backlog`; любой глагол сам добавляет issue на доску.
- `start` оставляет комментарий «Взял в работу. Сессия: <ссылка>» (из `CLAUDE_CODE_HOST_SESSION_ID`; нет переменной —
  предупреждение, не ошибка). `--comment "…"` дописывает текст.
- `wait` **требует** `--by` или `--comment` (иначе код 1). `--by 12` / `--by "#12"` → «Ждём #12.»; `--by` может быть и
  текстом: `--by "решения пользователя"`. Когда блокер снят — снова `start N`.
- `ready` — только когда изменение **в main** (смёрджено, тесты зелёные), а не когда готово на ветке.
- `done` — только когда изменение вошло в релиз; без указания пользователя не ставь.
- `ready` и `done` пишут комментарий только с `--comment`; полезно указать коммит: `--comment "5fc0e30"`.
- Глагол принимает один номер. Подтверждение — одна строка, перечитывать задачу не нужно:
  `#42 Backlog → In progress, comment left`.

## Чтение

- `gh dojo show N` — **перед началом работы**: статус, milestone, блокеры в обе стороны (неснятые первыми, у каждого
  статус на доске), история, описание, последние 5 комментариев. `gh dojo show 12 13 --brief` — по три строки на задачу; `--comments all` — весь тред (до 100);
  `--full` — без обрезки описания и комментариев.
- `gh dojo list` — открытые задачи по статусам (Done и закрытые скрыты со счётчиком). Фильтры:
  `--status "In progress"`, `--status none`, `--mine`, `--label bug`, `--all`, `--limit 100`.
- `gh dojo <глагол> N --dry-run` — план без изменений: что станет со статусом и какой комментарий уйдёт.

## Запись

- `gh dojo new "<заголовок>" --type <bug|enhancement|documentation|dogfood> --body "…"` — issue + метка + доска +
  `Backlog` одной командой. Длинное описание: `--body-file file` или `--body-file -` (stdin). Ещё метки: `--label X`.
  Заголовок с `-` — после `--`.
- `gh dojo comment N "текст"` или `gh dojo comment N --body-file -` — комментарий без смены статуса.

## Коды выхода

Полный список — в `gh dojo --help` (раздел Exit codes). Главное: при ошибке читай строки `error:` / `allowed:` /
`fix:`; код 2 — отказ проверки процесса: **не обходи** его (не двигай статус другим путём), спроси пользователя;
коды 4 и 5 — повтори **ту же** команду (4 — чуть позже).

Повтор безопасен: глагол не меняет уже выставленный статус и не пишет комментарий, если он уже последний от
gh-dojo; `comment` не дублирует свой последний комментарий; `new` с тем же заголовком доделывает уже созданную
issue, а не заводит вторую. Поэтому после кода 4 или 5 просто повтори команду.

## Неудобство → задача `dogfood`

Любое неудобство при работе с gh-dojo (непонятная ошибка, лишний шаг, не хватает флага, справка врёт, пришлось
обойти через `gh`) — **сразу** заводи задачу, не откладывая и не чиня молча:

```sh
gh dojo new "<что неудобно, кратко>" --type dogfood --body "Что делал: … Что ожидал: … Что получил: …"
```

Затем продолжай основную задачу.

## Чего нет в v0.0

Здесь допустим `gh`, но только когда это нужно по задаче или просит пользователь:

- закрыть или переоткрыть issue — `gh issue close N` / `gh issue reopen N` (`done` issue не закрывает);
- поправить заголовок, описание, метки или исполнителей существующей issue — `gh issue edit N …`;
- блокеры (`block` / `unblock`, `new --blocked-by`) — появятся в v0.1; пока связь blocked-by ставит пользователь в
  веб-интерфейсе, а ты пишешь `gh dojo wait N --by <номер>`;
- `describe`, `init`, `doctor`, `--json` — v0.1; `next`, `release`, `agent install` — v0.2 (этот skill пока написан
  вручную).

## Какая версия работает

Установленный `gh dojo` — сборка последнего `make install` из main, а не текущей ветки: сломанная ветка не ломает учёт
задач. Новое поведение из ветки в `gh dojo` не появится, пока его не смёрджат в main и не переустановят:

```sh
gh dojo --version   # git describe установленной сборки
make install        # в рабочей копии на main, после мёрджа
```
